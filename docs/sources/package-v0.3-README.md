## Перенос в GitHub

1. Сверить remote, актуальную базовую ветку, `git status`, существующую структуру `docs/`, инструкции проекта и workflow. Зафиксировать SHA базы, пути к движку, конфигу и фактическим командам тестов. Если есть расхождения со сводкой, приложить доказательство с SHA и воспроизводимым сценарием.
2. Создать отдельную ветку от чистой актуальной базы, например `docs/fight-club-v03`. Свести Markdown с текущими документами без потери исторических данных. Рекомендуемое расположение — `docs/GDD.md`, `docs/ROADMAP.md`, `docs/CHANGELOG.md`, `docs/BACKLOG.md`, `docs/QA_PLAN.md`, `docs/releases/v0.3.md` и `docs/sources/`. Корневой README проекта сохранить. При необходимости добавить ссылку на GDD отдельной согласованной правкой.
3. Два JSON сначала держать рядом с документацией как предложения. Если их перенос затрагивает существующий рантайм-конфиг, сначала рассмотреть схемы и пути проекта. **Никогда не подменять `docs/balance.json` файлом из архива.** Зафиксировать хеш существующего файла при аудите. Изменения параметров боя возможны отдельным согласованным PR с симуляциями.
4. Проверить ссылки, Markdown, JSON, чистоту diff и сохранность `docs/balance.json`. В PR описать DFC-001–005, предложенные настройки, расхождения с кодом и риск автодеплоя из `main`. Разработку вести в отдельных PR по [бэклогу](../BACKLOG.md), начиная с проверок базы.
5. После публикации проверить URL PR и видимость коммита на GitHub. После merge отдельно проверить SHA в целевой ветке. О выкладке сообщать только после проверки развёрнутой версии и smoke. Связать PR, отчёт QA и релиз в GDD/CHANGELOG.

Публикация этого пакета в GitHub не подтверждена. Исходный код, существующие конфиги и GitHub в рамках подготовки архива не изменялись.
